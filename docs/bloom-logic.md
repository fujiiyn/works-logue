# 開花ロジック（Seed が Logue になるまで）

Works Logue の中核である「開花」の仕組みを1枚にまとめたもの。ビジネスサイド向けの説明用。
数値・条件はすべて実装コード（`apps/api/app/pipelines/score_pipeline.py`、`apps/api/app/services/score_engine.py`、`apps/api/app/repositories/settings_repository.py`）を正としている。

---

## 一言で言うと

Seed（投稿された悩み）に Log（コメント）が付くたびに、AI がその議論を採点する。
採点は2段階で、**「知恵の形が揃っているか」→「その中身が成熟しているか」** の順に見る。
両方を満たした瞬間に、AI が議論をまとめた記事（Logue）を自動生成する。これが開花。

人が「まとめよう」と判断するのではなく、議論の中身が基準を超えた時点で自動的に起きる。

---

## 全体の流れ

```
ユーザーが Log を投稿
        │
        ▼
【条件A】知恵の形が揃っているか（毎回チェック）
   Context / Problem / Solution / Name の4つ
        │
        ├─ 4つ揃っていない ──→ 進捗バーだけ伸ばして終了
        │
        ▼ 4つ揃った
【条件B】議論の中身が成熟しているか
   網羅度 / 多様性 / 反論・例外 / 具体性 の4観点を採点、平均を出す
        │
        ├─ 平均が 0.90 未満 ──→ AI（Wisp）が足りない観点を突く問いかけを投稿
        │                        → 議論が続き、次の Log でまた採点
        │
        ▼ 平均が 0.90 以上
【開花】Logue を自動生成
   ・記事をパターンランゲージ形式で生成
   ・貢献者にインサイトスコアを付与
   ・以降その Seed には Log を投稿できなくなる（読み取り専用）
```

---

## 条件A：知恵の「形」が揃っているか

Seed 本文と全 Log を AI に渡し、ビジネスノウハウとして成立するための4つの部品が揃っているかを、それぞれ有り／無しで判定する。

| 部品 | 中身 | 揃ったと判定される条件 |
|---|---|---|
| Context（状況） | どんな前提・環境で起きる話か | 具体的な状況説明がある |
| Problem（問題） | そこで何に詰まるのか | 課題や困難が明確に言語化されている |
| Solution（解決策） | どう突破したのか | 実行可能なアクションが提示されている |
| Name（パターン名） | このノウハウに名前が付くか | 上の3つが揃い、他社でも使える形になっている |

**充足率 = 揃った部品数 ÷ 4**。4つすべて揃って `1.0`（100%）になった時に、はじめて条件Bに進む。
つまり、どれだけコメントが盛り上がっても「解決策が出ていない」議論は条件Bに進まない。

---

## 条件B：議論の「中身」が成熟しているか

条件Aを満たした議論だけが対象。AI が4つの観点を 0.0〜1.0 で採点し、その**平均**を成熟度スコアとする。

| 観点 | 見ているもの |
|---|---|
| 網羅度（comprehensiveness） | 原因・対策・予防策など、テーマ全体を俯瞰できているか |
| 多様性（diversity） | 異なる背景を持つ複数ユーザーの視点が含まれているか |
| 反論・例外（counterarguments） | 「このケースでは逆効果」のような検証ログがあるか |
| 具体性（specificity） | 明日から実行できるレベルのアクションが取り出せるか |

**成熟度スコアが 0.9 以上で開花。**

反論・例外を独立した観点として採点しているのが要点。賛同コメントばかり集まっても成熟度は上がらず、開花に至らない。

多様性も同じ働きをする。Log を書いているのが1人だけの Seed では、多様性スコアが 0.7〜0.8 で止まり、平均が 0.9 に届かない。つまり、複数人の Log が集まらない限り開花しない。

---

## 進捗バーの意味

ユーザーに見えている進捗バーは、条件Aと条件Bで前半・後半を分担している。

| 表示 | 進捗 | 中身 |
|---|---|---|
| Seed（Log 0件） | 0% | 未評価 |
| 芽 | 0〜50% | 条件Aが進行中（例：2/4 揃って 25%） |
| 成長 | 50〜80% | 条件A充足、条件Bが進行中 |
| 蕾 | 80〜99% | 開花が目前 |
| Logue | 100% | 開花済み |

前半50%が条件Aの充足率、後半50%が条件Bの成熟度に対応する。

**進捗は後戻りしない。** AI の判定は毎回わずかに揺れるため、そのまま反映すると進捗バーが下がって見えてしまう。実装では前回の評価と比較して高い方を採用しているので、ユーザーから見て進捗が減ることはない。

---

## 開花に届かないとき：Wisp が議論を進める

成熟度が 0.9 に届かない場合、AI ファシリテーター **Wisp** が最もスコアの低い観点を特定し、それを埋める問いかけを Log として投稿する。

- 例：反論・例外のスコアが低ければ、「逆にうまくいかなかったケースはありますか」といった方向で問いかける
- Wisp が連投して議論を支配しないよう、**前回の Wisp 投稿以降にユーザー Log が3件以上付くまで**次の投稿を抑制する
- Wisp の投稿は**採点の対象に含めない**（AI の言葉で成熟度が上がってしまうのを防ぐため）

つまり議論が停滞したとき、放置ではなく AI が次の一手を提示する。

---

## 開花したあとに起きること

1. Seed の状態が `logue` に変わり、進捗が 100% になる
2. AI が記事を生成する。構成は**パターンランゲージ形式の6セクション**（パターン名 / 状況 / 問題 / 解決策 / 反論・例外 / 出典）
3. 出典は脚注方式。本文中の `[1]` `[2]` から、引用元の Log（投稿者名 + 抜粋）を辿れる
4. 貢献者に**インサイトスコア**が付与される。AI が各 Log の記事への貢献度を 0.0〜1.0 で評価し、Seed 投稿者には固定で 1.0 のボーナスが付く。開花時に1回だけ計算し、以降は再計算しない
5. その Seed には新しい Log を投稿できなくなる。開花は1回のみで、元の状態には戻せない

記事生成には数十秒かかるため、その間ユーザーには開花処理中の画面が表示される。

---

## 運用で調整できる数値

管理画面（Admin）から変更できる。

| 設定キー | 現在値 | 意味 |
|---|---|---|
| `score.bloom_threshold` | 0.9 | 開花に必要な成熟度スコア |
| `score.bud_threshold` | 0.8 | 蕾（開花目前）表示に切り替わる進捗 |
| `score.min_contributors` | 3 | **現在は未使用**（旧仕様の名残。将来の再導入用に値だけ残している） |
| `score.min_logs` | 5 | **現在は未使用**（同上） |

開花のハードルを上げ下げしたい場合は `bloom_threshold` を動かす。数値を上げれば記事の質は上がるが開花数は減る。

---

## 設計上の判断とその理由

| 判断 | 理由 |
|---|---|
| 条件Aを満たすまで条件Bを評価しない | 形が揃っていない議論に成熟度を測る意味がなく、AI 呼び出しコストも無駄になる |
| 最低参加者数・最低 Log 数のゲートを撤廃（2026-05-06） | 「参加者3人以上」といった量の条件は、少人数でも質の高い議論を止めてしまう。質の判定（条件A・B）に一本化した |
| 採点を Log 投稿ごとに毎回実行 | 進捗をリアルタイムに見せることが、共創の熱量を可視化する仕組みそのものになっている |
| 採点は投稿完了後にバックグラウンドで実行 | 採点に AI 呼び出しが入るため、待たせずに投稿を完了させる。採点が失敗しても投稿は残る |
| Wisp の投稿を採点対象から除外 | AI 自身の言葉で成熟度が上がると、人の知恵が集まっていないのに開花してしまう |
| 開花基準を 0.85 から 0.9 に引き上げ（2026-10-03） | Log が少ないうちに開花すると記事が薄くなり、AI が一般論で埋める余地が大きくなるため。1人だけの Seed が開花しなくなるが、複数人の Log が集まってから開花させるために受け入れる |
